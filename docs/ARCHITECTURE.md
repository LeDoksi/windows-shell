# Архитектура и оценка осуществимости

Документ — разбор [исходного MVP](mvp-v2-original.md) и [концепта](concept.png): что реально, где риски, что предлагаю сделать иначе.

## TL;DR

- **Идея целиком осуществима** на Windows 11. Ничего из MVP не требует внедрения в Explorer или драйверов: всё делается обычными Win32/COM API из отдельного процесса.
- **Стек оставляем: Tauri 2 + React + TypeScript.** Версии из документа реальные (Tauri 2.12, React 19.3). Rust-часть даёт прямой доступ к Win32 через крейт `windows`, фронт даёт скорость итераций по дизайну.
- **Главный технический риск — «стекло».** Настоящий blur того, что под окном, делает только DWM (Acrylic), и он заливает весь прямоугольник окна. Для дока с увеличением иконок это конфликт. Решается, но нужно проверить спайком **до** полировки UI (см. ниже).
- **Второй риск — фокус и z-order.** Dock не должен красть фокус у приложений и должен уверенно держаться поверх окон. Тоже решаемо, тоже в спайк.
- **Третий риск — свой трей.** Штатный Taskbar убираем совсем, поэтому иконки фоновых программ принимаем сами (подход ManagedShell/Cairo Desktop). Подробно в [SYSTEM-TAIL.md](SYSTEM-TAIL.md).
- **Аудио-виджет полностью реален**: громкость, mute, по-приложениям, переключение устройства по умолчанию. Одна часть (смена дефолтного устройства) идёт через недокументированный, но давно стабильный `IPolicyConfig` — им пользуются EarTrumpet, SoundSwitch, nircmd.

## Почему Tauri, а не альтернативы

| Вариант | За | Против | Вывод |
|---|---|---|---|
| **Tauri 2 + React** | Лёгкий (WebView2 уже в Windows 11), Rust для Win32, быстрые итерации UI, легко писать виджеты | Каждое окно — отдельный WebView; blur только через DWM | **Берём** |
| WinUI 3 / C# | Нативный Acrylic/Mica, Composition-анимации | Медленнее итерации дизайна, тяжелее упаковка, тот же «прямоугольник» у backdrop | Запасной вариант, если спайк по стеклу провалится |
| Electron | Знакомо | Тяжёлый (свой Chromium на каждое окно-процесс), без выгоды над Tauri | Нет |
| Rust native (egui/iced/slint) | Быстро, мало памяти | Glass-эстетика и анимации — всё вручную | Нет |

Память: одно приложение, ~5–7 WebView-окон в одном WebView2-окружении (общий браузерный процесс). Ожидаемо 80–150 МБ. Для оболочки, которая висит всегда, приемлемо; окна категорий и настроек создаём лениво и уничтожаем при закрытии.

## Окна

Один процесс, несколько окон без рамок:

| Окно | Поведение |
|---|---|
| `launcher` (верхняя панель) | topmost, autohide, не в Taskbar/Alt+Tab, при закреплении — AppBar (резервирует место, развёрнутые окна не залезают) |
| `category` (окно категории) | popover под панелью, закрывается по клику мимо/Esc |
| `dock` | topmost, autohide, **без активации** (`WS_EX_NOACTIVATE`), не в Alt+Tab |
| `flyout` | popover: виджеты под верхней панелью, список окон приложения над доком |
| `search` | центр экрана, по хоткею, получает фокус |
| `settings` | обычное окно |

Реализация (WSH-14): окна создаёт Rust при старте (`src-tauri/src/shell.rs`), фронт рисует часть интерфейса по метке окна (`src/windows/ShellWindows.tsx`), окна общаются событиями (`category_open`, `flyout_open`, `system_state` …) через `backend.emit`. Все окна — `WS_EX_TOOLWINDOW` (не в Alt+Tab). Док — два окна по итогам спайков (`src-tauri/src/dock.rs`): подложка с Acrylic и окно иконок без активации, возврат фокуса и подъём над topmost-окнами. Прозрачная часть окна WebView2 перехватывает клики, поэтому окно панели подгоняется под ширину самой панели; поповеры закрываются, когда их окно теряет фокус. Браузерный режим (`pnpm dev:web`) по-прежнему рисует всё на одной странице.

Стекло (WSH-15): настройка `appearance.glass` в конфиге — `"acrylic"` («Стекло», по умолчанию) или `"tint"` («Тонировка»), только ручной выбор. В режиме «Стекло» под таблеткой дока и под верхней панелью лежат окна-подложки `<окно>-backdrop` с DWM Acrylic: окно сообщает прямоугольник элемента (`glass_rect`), Rust ставит подложку и переставляет её, когда окно сдвигается. В режиме «Тонировка» подложки спрятаны, фон даёт CSS на плотных токенах (`data-glass="off"`). Переключение — по `config_changed`, без перезапуска; после показа подложки окно с содержимым поднимается над ней. Поповеры (категория, поиск, flyout) пока на тонировке в обоих режимах.

Значок в трее (WSH-18, `src-tauri/src/tray.rs`): меню «Стекло» / «Тонировка» (галочки следуют за конфигом), «Перезапустить», «Выход». Значок — обычный `Shell_NotifyIcon` через Tauri, штатный трей не трогаем.

### Стекло (главный риск)

- CSS `backdrop-filter` внутри прозрачного WebView2 размывает только содержимое самой страницы, **не рабочий стол и не окна под ней**. Для «настоящего» glass нужен DWM backdrop: `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE, DWMSBT_TRANSIENTWINDOW)` (Acrylic, Win11 22H2+) или крейт `window-vibrancy`.
- DWM заливает **весь прямоугольник окна**, а скругление углов у DWM фиксированное и маленькое (`DWMWA_WINDOW_CORNER_PREFERENCE`).
- Dock с magnification требует окна выше самой «таблетки» (иконки растут вверх) — значит, backdrop будет торчать над доком.

Варианты, которые проверяет спайк:
1. **Два окна для дока**: снизу окно-подложка ровно по размеру таблетки с Acrylic, сверху прозрачное окно с иконками, которое может быть выше. Подложку анимируем вместе с шириной дока. Скорее всего это и будет решение.
2. Одно окно + `SetWindowRgn` со скруглённым регионом. Минус: регион без сглаживания, края «лесенкой».
3. Фолбэк без blur: полупрозрачная тонировка + тень + тонкая обводка. По концепту (бирюзовые обои) это выглядит почти так же, и это надёжно. Дизайн-система рассчитана так, чтобы фолбэк выглядел достойно.

#### Итог спайка (WSH-4, Windows 11, октябрь 2026)

Проверено на живом рабочем столе, снимки: [`spike-glass.png`](spike-glass.png). Код спайка: `src-tauri/src/spike.rs`, запуск `WS_SPIKE=a|a-blur|b|c pnpm tauri dev --features spike`.

**Решение: вариант 1 (два окна), с тремя обязательными доработками. Фолбэк — вариант 3.**

- Подложка-окно с `DWMSBT_TRANSIENTWINDOW` следует за шириной таблетки без видимого отставания: фронт каждый кадр отдаёт прямоугольник таблетки, Rust двигает подложку одним `SetWindowPos`. Иконки растут вверх над подложкой, подложка выше таблетки не торчит.
- **DWM рисует Acrylic только у активного окна**, у неактивного — серая заливка. Док активным не бывает, поэтому подложке шлём `WM_NCACTIVATE(TRUE)` и подменяем этот же флаг в subclass-обработчике. После этого стекло держится при кликах по другим окнам.
- **Клик по доку не должен активировать окна дока** — иначе подложка гаснет в серое. Как этого добиться, см. «Итог спайка WSH-5» ниже: одного `WS_EX_NOACTIVATE` мало.
- **`SetWindowRgn` DWM-подложку не обрезает**: регион режет содержимое окна, но размытие остаётся на весь прямоугольник с квадратными углами. Скругление — только штатное `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`: гладкое, с тенью DWM, но фиксированный радиус ≈ 8 px. Значит, радиус таблетки дока в CSS должен быть 8 px (не `--ws-radius-xl`), иначе обводка не совпадёт с краем стекла.
- Вариант 2 (одно окно + регион) отпал: размытие торчит на всю высоту окна над доком, а регион при этом обрезает увеличенные иконки.
- `SetWindowCompositionAttribute` с `ACCENT_ENABLE_BLURBEHIND` (`a-blur`) в прозрачном окне WebView2 даёт чёрную подложку — не годится.
- Вариант 3 (тонировка + обводка + тень) выглядит прилично и ничего не требует от DWM. В продукте оба режима, выбор — только тумблером в настройках (`appearance.glass`), без автоматического переключения. Где Acrylic недоступен (Windows 10, выключены «Эффекты прозрачности»), режим A покажет серую подложку; пользователь сам переключит на C.

### Autohide и наведение к краю

- Скрытое окно не получает события мыши. Вместо глобального хука `WH_MOUSE_LL` (антивирусы его не любят) — поток в Rust опрашивает `GetCursorPos` ~60 раз в секунду, это копейки по CPU. Срабатывание с задержкой ~150 мс, чтобы панель не выскакивала, когда курсор просто пролетает к кнопке закрытия окна.
- Не показываться поверх полноэкранных игр/видео: `SHQueryUserNotificationState` + проверка, что foreground-окно покрывает монитор.
- Мультимонитор и DPI: per-monitor DPI v2, все позиции считаем в физических пикселях конкретного монитора, переподписываемся на `WM_DISPLAYCHANGE`.

#### Итог спайка WSH-6: автоскрытие, полноэкранные приложения, мониторы и DPI (Windows 11, октябрь 2026)

Код: `src-tauri/src/spike_autohide.rs`, запуск `WS_AUTOHIDE=1 WS_SPIKE=a pnpm tauri dev --features spike`, монитор — `WS_MONITOR_AT=x,y`. Проверено скриптом на ПК с тремя мониторами: 2560×1440 100 % (основной), 2560×1440 100 % слева, 3840×2160 175 % ещё левее (координаты x от −6400).

- **Опрос курсора работает и почти бесплатен**: поток в Rust, `GetCursorPos` каждые 16 мс, полноэкранный режим раз в ~250 мс. Нагрузка — 0–47 мс CPU за 10 с, то есть до 0,5 % одного ядра; в простое 0. Глобальный хук мыши не нужен.
- **Поведение**: курсор у нижнего края в пределах ширины таблетки дольше 150 мс — док выезжает (100 мс у края — ещё спрятан, касание на 60 мс — не выезжает). Пока курсор над доком (включая полосу под ним до края экрана) — не прячется; ушёл — прячется через 400 мс. Выезд — 180 мс, ease-out. Логика — чистая функция `Autohide::tick`, покрыта unit-тестами.
- **Подложка и иконки едут синхронно**: оба окна двигаются одним `BeginDeferWindowPos`/`EndDeferWindowPos`; на кадрах посреди выезда смещение между ними постоянное. Спрятанный док — окно целиком ниже края монитора. Если под монитором есть другой монитор, док будет на нём виден — тогда прятать через `SW_HIDE` после анимации (не проверено, такого расположения нет).
- **Полноэкранные приложения**: док не выезжает, если `SHQueryUserNotificationState` = 2/3/4 или активное окно закрывает свой монитор (рабочий стол `Progman`/`WorkerW` и `Shell_TrayWnd` не считаются). Проверено окном без рамки на весь экран и видео на весь экран в Edge (кнопка «на весь экран» у элемента) — в обоих случаях док остался спрятан, после выхода снова выезжает.
- **DPI: размеры дока на мониторе считаем сами**, в физических пикселях: логический размер × `GetDpiForMonitor(MDT_EFFECTIVE_DPI)/96`, по центру низа `rcWork` (функция `dock_rect`, тесты для 100/125/150 % и отрицательных координат). На мониторе 175 % окно иконок 2100×333 вместо 1200×190, иконки отрисованы в правильном масштабе.
- **Подвох 1**: окно, сразу поставленное ниже края монитора, не получает `WM_DPICHANGED`. Поэтому при смене раскладки окно сначала ставим на сам монитор, потом прячем.
- **Подвох 2**: `WM_DPICHANGED` первым обрабатывает Tauri и задаёт свой размер; свою раскладку делаем после него (в subclass — после `DefSubclassProc`), иначе Tauri её перетирает.
- **Подвох 3**: физические пиксели таблетки считаем во фронте через `devicePixelRatio` WebView2, а не через `scale_factor()` окна Tauri — на мониторе 175 % после переезда они расходились, и подложка становилась почти вдвое больше таблетки. С `devicePixelRatio` подложка совпадает с таблеткой и на 100 %, и на 175 %.
- **Подвох 4 (только для тестов)**: процесс, который проверяет координаты, тоже должен быть per-monitor v2 — иначе Windows отдаёт ему «ужатые» координаты окон на мониторе 175 %.
- Поток опроса уже per-monitor v2 (это настройка процесса Tauri), но ставим явно `SetThreadDpiAwarenessContext`, чтобы не зависеть от этого.
- Пересчёт раскладки — по `WM_DISPLAYCHANGE`, `WM_DPICHANGED`, `WM_SETTINGCHANGE` (рабочая область). Смену конфигурации мониторов по-настоящему не проверяли (настройки дисплея не трогали), только имитацией `WM_DISPLAYCHANGE`.
- Не проверено: увеличение иконок под курсором на мониторе 175 % (курсор двигал скрипт, на скриншоте увеличения нет) и перетаскивание дока между мониторами на лету — это задача этапа 2 «Выбор монитора, DPI».

#### Этап 2 (WSH-16): автоскрытие и закрепление в оболочке

Код: `src-tauri/src/bars.rs`. Механика спайка WSH-6 для обеих полос — верхней панели (выезжает сверху) и дока (снизу). Открытый поповер (категория, поиск — для панели; flyout — для дока) держит полосу показанной. Закрепление — пункты «Закрепить панель» / «Закрепить док» в меню трея (`bars` в конфиге, по умолчанию обе полосы автоскрываемые). Закреплённая полоса регистрируется как AppBar и резервирует место до дальнего края своего «стеклянного» элемента + 8 px (панель — 72 px при 100 %, док — 92 px над панелью задач); развёрнутые окна её не перекрывают. При выходе (и перед «Перезапустить») AppBar снимается — проверено: рабочая область возвращается к исходной. Монитор полос (WSH-17) — подменю «Монитор» в трее (`bars.monitor`, имя устройства Windows; не подключён — основной). Раскладку мониторов поток опроса перечитывает дважды в секунду, так что подключение, разрешение и масштаб подхватываются без подписок на `WM_DISPLAYCHANGE`. При смене монитора полосы сначала выставляются на старом мониторе, потом на новом: спрятанная полоса за краем не на мониторе и без этого не получает `WM_DPICHANGED` (проверено — панель осталась в масштабе 175 % на мониторе 100 %). Окна категории и поиска переносятся с размером в физических пикселях. Проверено на ПК: основной 100 % → 3840×2160 175 % (размеры ×1,75, выезд, закрепление резервирует место на том мониторе) → обратно. Не проверено: монитор над/под другим (спрятанная полоса будет видна на соседнем) и отключение монитора на лету (только по коду: выбранного нет — основной).

### Z-order

Другие topmost-окна (и Taskbar, если Explorer его на миг покажет) могут оказаться выше. Dock слушает `EVENT_SYSTEM_FOREGROUND` и при необходимости возвращает себя наверх (`SetWindowPos(HWND_TOPMOST)` без активации).

#### Итог спайка WSH-5: без активации и topmost (Windows 11, октябрь 2026)

Проверено скриптом на живом рабочем столе: тестовый редактор, чужое topmost-окно, развёрнутое и полноэкранное окна, Alt+Tab. Код в `src-tauri/src/spike.rs` (`--features spike`, `WS_NOBG=1` — без тестового фона, `WS_NORAISE=1` — без возврата наверх).

- **`WS_EX_NOACTIVATE` и `MA_NOACTIVATE` на `WM_MOUSEACTIVATE` не спасают**: на клик WebView2 сам зовёт `SetFocus` своему окну ввода, и окно дока становится активным, а чужое приложение теряет фокус. `preventDefault` на `mousedown` во фронте тоже не помогает.
- **Решение — вернуть фокус**: хук `EVENT_SYSTEM_FOREGROUND` запоминает последнее чужое активное окно; если активным стал док, сразу `SetForegroundWindow(предыдущее)`. В этот момент foreground — мы, поэтому Windows это разрешает. Результат: печатаем в редакторе «hello», два клика по доку, печатаем « world» — в редакторе «hello world», клики по иконкам срабатывают. Цена: заголовок чужого окна на долю секунды мигает «неактивным».
- Стили всё равно оставляем (`WS_EX_NOACTIVATE` на обоих окнах + `MA_NOACTIVATE`): они убирают активацию там, где WebView2 не вмешивается.
- **Окно иконок не должно быть «владеемым» подложкой.** С отношением owner краткая активация иконок навсегда гасит Acrylic у подложки, и повторный `WM_NCACTIVATE(TRUE)` уже не помогает. Без owner стекло держится; порядок «подложка ниже иконок» задаёт `raise_dock` (сначала подложка, потом иконки).
- **Topmost**: чужое topmost-окно становится активным раньше, чем ставит себе `TOPMOST`, поэтому одного подъёма в хуке мало — повторяем через 80 и 300 мс. После этого док снова над ним. Над развёрнутым и над полноэкранным окном без рамки док тоже сверху.
- **Полноэкранный режим**: `SHQueryUserNotificationState` для окна без рамки на весь экран (так выглядит видео в браузере на весь экран) вернул `QUNS_BUSY` (2), в обычном режиме — `QUNS_ACCEPTS_NOTIFICATIONS` (5). Сейчас док остаётся поверх полноэкранного окна — это неправильно; прятать его при 2/3/4 будем в спайке autohide (WSH-6).
- **Alt+Tab и панель задач**: окон дока нет ни там, ни там (`skip_taskbar` + `WS_EX_NOACTIVATE`), отдельный `WS_EX_TOOLWINDOW` не понадобился.
- Риск на потом: если WebView2 перестанет воровать фокус (или перейдём на composition-хостинг WebView2, где ввод передаёт хост), возврат фокуса можно убрать.

## Запуск объектов

- Файлы, папки, `.lnk`, URL: `ShellExecuteExW` (то же, что двойной клик в Explorer).
- UWP/Store-приложения: `shell:AppsFolder\<AUMID>`.
- «Открыть расположение»: `SHOpenFolderAndSelectItems` (открывает папку с выделенным файлом).
- Иконки: `IShellItemImageFactory` в 256px (работает и для exe, и для UWP, и для папок), кэш PNG в `%LOCALAPPDATA%`.
- Удаление из панели трогает **только конфиг**. В коде вообще не будет функций, удаляющих/перемещающих пользовательские файлы, — это проще проверить, чем обещать.

## Работа с окнами (ядро дока)

- Список окон: `EnumWindows` + фильтры (видимое, без владельца, не `WS_EX_TOOLWINDOW`, не «cloaked» через `DWMWA_CLOAKED` — так отсекаются окна других виртуальных столов и спящие UWP).
- **Группировка по AppUserModelID**, а не по exe: иначе все UWP-приложения склеятся в `ApplicationFrameHost.exe`, а PWA из Chrome — в Chrome. AUMID берём через `SHGetPropertyStoreForWindow`, фолбэк — путь exe.
- Без поллинга: `SetWinEventHook` на создание/уничтожение/показ/скрытие окон, смену foreground и заголовка. Rust держит модель «приложение → окна» и шлёт diff во фронт.
- Фокус: `SetForegroundWindow` ограничен Windows. Так как клик по доку — пользовательский ввод в наш процесс, право на смену foreground у нас есть; для надёжности — `AllowSetForegroundWindow`/`AttachThreadInput`. Свёрнутое окно — `ShowWindow(SW_RESTORE)`.
- Поведение клика (как в Windows): не запущено → запустить; запущено, но не активно → активировать; активно → свернуть; несколько окон → popup со списком. Поэтому доку и нужен `NOACTIVATE`: иначе в момент клика активным всегда будет сам док.

Реализация (этап 4, WSH-25…29):

- **Трекер** — `src-tauri/src/apps.rs`. Свой поток с невидимым окном: `SetWinEventHook` (создание/показ/скрытие, свернуть/развернуть, заголовок, cloak, foreground) и shell hook (`HSHELL_FLASH` — окно мигает). Событие только ставит таймер на 60 мс, после чего полный пересчёт `EnumWindows`; страховочный пересчёт раз в 2 с. Изменился список — `windows_changed` всем окнам. Хуки зовутся и посреди COM-вызовов пересчёта, поэтому они лишь складывают события в очередь.
- **Окно** (`WindowInfo`): `hwnd`, заголовок, AUMID (свойство окна, иначе AUMID упакованного процесса; у UWP — процесс из дочернего `CoreWindow`, а не ApplicationFrameHost), exe, название приложения («Пуск» → описание exe → имя файла), свёрнуто, активно, мигает, порядок появления и время последней активации. Активное — последнее чужое foreground-окно, приведённое к корневому владельцу: клик по доку на миг делает активным сам док, это не считается.
- **Группировка** — во фронте (`src/dock/model.ts`): окно ищет закреплённое сначала по AUMID, потом по exe (exe закреплённого по AUMID даёт `app_targets` — цель ярлыка из «Пуска»). Остальные окна — незакреплённые иконки по AUMID или exe, в порядке появления.
- **Клик**: не запущено → запустить; не активно → показать последнее активное окно; активно и окно одно → свернуть; активно и окон несколько → меню со списком окон. Правый клик — то же меню: окна, «Новое окно», «Закрепить в доке» / «Убрать из дока», «Закрыть окно» / «Закрыть все окна». Средний клик — новое окно. Меню — своё окно `dock-menu`, подгоняется под размер меню над иконкой.
- **Удалённые приложения**: `app_targets` проверяет AUMID через `shell:AppsFolder`; закреплённая иконка тускнеет с подсказкой «Не найдено», плитка в категории тоже.

## Состояние и конфиг

- Несколько окон = несколько отдельных JS-контекстов. **Источник правды — Rust**: он владеет конфигом и живыми данными (окна, аудио), окна получают события и шлют команды. Во фронте — тонкий стор, который подписан на события.
- Конфиг: `%APPDATA%\WindowsShell\config.json`, с `schemaVersion` и миграциями, атомарная запись (temp + rename), бэкап последней версии. У всех элементов стабильные `id`.
- Для приложений храним не только путь, но и AUMID (если есть): путь к exe меняется при обновлениях (Discord, Teams, Steam-игры).

## Taskbar

Решение (2026-10-02): штатный Taskbar убираем совсем, Windhawk не используем. Часы, сеть, звук, батарея (только на ноутбуке) и трей фоновых программ живут в системном хвосте дока. Как прячем Taskbar, как возвращаем его при падении и как принимаем иконки трея — в [SYSTEM-TAIL.md](SYSTEM-TAIL.md).

### Итог спайка WSH-43: прячем Taskbar и возвращаем (Windows 11, октябрь 2026)

Проверено на ПК с тремя мониторами (три окна панели: `Shell_TrayWnd` + два `Shell_SecondaryTrayWnd`), с разрешения владельца. Код: `src-tauri/src/spike_taskbar.rs`, запуск `WS_TASKBAR=hide WS_SPIKE=c pnpm tauri dev --features spike`. Аварийный возврат без нашего exe: `scripts/restore-taskbar.cmd`.

**Решение: прячем так, как описано в SYSTEM-TAIL.md (автоскрытие + `SW_HIDE` всех окон панели), возврат — четырьмя независимыми путями.**

- **Сначала сохраняем, потом меняем.** Исходное автоскрытие (`ABM_GETSTATE`) пишется в `%LOCALAPPDATA%\WindowsShell\taskbar-state.txt`, затем запускается сторож, и только потом включаем автоскрытие и прячем окна. Есть файл — значит, панель «наша» и её надо вернуть.
- **Пути возврата**: (1) обычный выход (`RunEvent::Exit`) и паника (panic hook); (2) процесс-сторож — тот же exe с `--taskbar-watchdog <pid>`, без окна, ждёт смерти основного процесса через `WaitForSingleObject`; (3) следующий запуск: файл состояния остался — сперва возвращаем; (4) `scripts/restore-taskbar.cmd` (PowerShell, не зависит от сборки). Плюс `--restore-taskbar` у самого exe.
- **Проверено**: обычный выход (`taskkill` без `/F`) — вернул основной процесс; `taskkill /F` — вернул сторож; в обоих случаях автоскрытие, видимость всех трёх панелей и рабочая область совпали с исходными. Аварийный скрипт проверен до написания кода прятанья. В конце всё как было: автоскрытие выключено, три панели видны, рабочая область 2560×1392.
- **Рабочая область**: при автоскрытии Explorer сам отдаёт место панели — на основном мониторе 2560×1440 вместо 2560×1392. Док место не резервирует (он сам автоскрываемый, поверх окон); закреплённой верхней панели launcher место резервирует AppBar (этап 2). Подвох для тестов: `Screen.WorkingArea` в .NET кэширует значение в процессе — мерить в свежем процессе.
- **Explorer показывает панель сам**: сразу после включения автоскрытия он заново показывает вторичные панели — их прячет фоновая проверка (каждые 500 мс, в логе «hidden again (poll)» через ~0,5 с после старта). Показ панели извне прячется за ≤ 500 мс. `TaskbarCreated` (рассылается после перезапуска Explorer) обрабатываем: снова включаем автоскрытие и прячем. Проверено имитацией сообщения окну дока; настоящий перезапуск `explorer.exe` не делали — он закрыл бы открытые у владельца окна Проводника.
- **Клавиша Win** при спрятанной панели открывает меню «Пуск» как обычно, панель не появляется.
- Не проверено: настоящий перезапуск Explorer, смена конфигурации мониторов при спрятанной панели, хоткеи вроде Win+T (фокус на панель).

### Итог спайка WSH-44: свой трей (Windows 11 25H2, build 26200, октябрь 2026)

Проверено на ПК владельца с его разрешения. Код: `src-tauri/src/spike_tray.rs`, запуск `WS_TRAY=1 WS_SPIKE=c pnpm tauri dev --features spike`. Сторож и аварийный возврат — те же, что у WSH-43 (`guard(tray = true)`, `scripts/restore-taskbar.cmd`).

**Решение: подход ManagedShell/Cairo работает на 25H2. Своё скрытое topmost-окно `Shell_TrayWnd` принимает иконки и сразу пересылает всё штатному трею — Explorer продолжает работать как раньше.**

- **Как устроено**: окно класса `Shell_TrayWnd` (`WS_EX_TOPMOST | WS_EX_TOOLWINDOW`, без размера) в своём потоке; раз в секунду поднимаем его выше окна Explorer, потому что `Shell_NotifyIcon` ищет `FindWindow("Shell_TrayWnd")` по z-order. После создания рассылаем `TaskbarCreated` — программы заново добавляют иконки, уже через нас. Каждый `WM_COPYDATA` (иконки, AppBar и прочее) пересылаем окну Explorer через `SendMessageTimeout` и возвращаем его ответ.
- **Какие иконки пришли**: все 20 — от 17 программ: Steam, Discord, Chrome, Claude, Xbox, Wallpaper Engine, ShareX, MSI Afterburner, RTSS, Fan Control, MSI Center, Logitech G HUB, AmneziaVPN, DeepCool, Безопасность Windows, плюс две системные иконки Explorer (Bluetooth, громкость). Новая программа, запущенная при работающем трее, попала и к нам, и в трей Explorer.
- **Разбор `SHELLTRAYDATA`**: подпись `0x34753423`, `NIM_*`, `NOTIFYICONDATAW` с 32-битными хэндлами (hWnd +4, uID +8, uFlags +12, uCallbackMessage +16, hIcon +20, szTip +24, dwState +280, uVersion +800). Функции `parse`/`apply` — чистые, покрыты unit-тестами. Хэндлы иконок из чужих процессов годятся у нас (`GetIconInfo` успешен для всех 20) — их можно рисовать в доке.
- **Версии**: почти все программы на старой версии 0 (клик приходит как `lParam = событие`), версию 4 объявили Xbox и Wallpaper Engine (`lParam = (событие, uID)`, `wParam = точка привязки`).
- **Клики**: перед пересылкой `AllowSetForegroundWindow(pid)` владельца. Тестовая программа (WinForms, версия 0) получила левый клик, двойной клик и правый клик с открытием своего меню. Правый клик по Steam (версия 0) и по Wallpaper Engine (версия 4) открыл их настоящие контекстные меню, Esc закрыл.
- **Возврат**: при обычном выходе закрываем своё окно и рассылаем `TaskbarCreated`; при `taskkill /F` окно умирает вместе с процессом, а рассылку делает сторож. После обоих случаев трей Explorer принимает новые иконки (`Shell_NotifyIcon` NIM_ADD/NIM_DELETE → TRUE), панели и автоскрытие как были. `restore-taskbar.cmd` тоже рассылает `TaskbarCreated`, если в файле состояния `tray=1`.
- **Подвох**: окну `Shell_TrayWnd` шлют не только иконки. Пришло несколько `0x4EF` (WM_USER+239) — их не пересылаем (могут содержать указатели), видимых проблем не было. Пока наш трей работает, программы, которые ищут `Shell_TrayWnd`, чтобы узнать положение панели задач, найдут наше окно нулевого размера — в продукте окно надо ставить в место панели (как Cairo).
- **Ошибка в тесте**: из-за бага в тестовом скрипте первые клики ушли иконке Bluetooth Explorer и открыли окно «Параметры → Bluetooth и устройства». Ничего не изменилось, окно закрыто. Вывод на будущее: кликать только по иконке, найденной по имени процесса, и останавливаться, если её нет.
- Не проверено: всплывающие уведомления (`NIF_INFO`) — пересылаются Explorer, отдельно не смотрели; отрисовка иконок в доке (HICON → PNG) — задача этапа 8.
