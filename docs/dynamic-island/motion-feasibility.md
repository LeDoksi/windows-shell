# Жидкий motion — предварительная техническая оценка

2026-11-02. Только чтение документации и текущего кода; без прототипа, сборок,
установки зависимостей или изменений работающей оболочки.

## Вывод и границы уверенности

У эффекта есть техническая основа в Windows App SDK. Это аргумент в пользу
исследования нативного пути, а не доказательство, что нужный эффект уже работает
в нашей оболочке. Обещать конкретную плавность, тень и стоимость ресурсов рано.

## Проверенные первичные источники

- [PathKeyFrameAnimation, Microsoft.UI.Composition, Windows App SDK 1.8](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.pathkeyframeanimation?view=windows-app-sdk-1.8):
  API описывает анимацию между ключевыми контурами CompositionPath. Это возможный
  строительный блок для изменения силуэта; не готовая симуляция жидкости и не
  автоматическая деформация всего верхнеуровневого окна.
- [CompositionGeometricClip, Microsoft.UI.Composition, Windows App SDK 1.8](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.compositiongeometricclip?view=windows-app-sdk-1.8):
  видимая часть Visual определяется геометрией. Это основа для ограничения
  отрисовки формой; область приёма мыши и внешняя тень требуют отдельных решений.
- [CreateSpringVector3Animation](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.compositor.createspringvector3animation?view=windows-app-sdk-1.8):
  создаёт пружинную анимацию вектора. Наличие этого API не означает, что любой
  произвольный контур можно напрямую анимировать одной пружиной.

Это актуально просмотренные Microsoft.UI.Composition API, а не молчаливый перенос
примеров Windows.UI.Composition/UWP в WinUI 3. Точную совместимость с используемой
версией пакета и выбранными геометриями всё равно нужно подтвердить исполнением.

## Что есть в текущем коде

Прочитаны `native/Shell/Ui/ShellWindow.cs` и `native/Shell/Ui/Theme.cs`
соседнего `windows-shell`. ShellWindow уже имеет `Surface.Transparent` через
установленный WinUIEx `TransparentTintBackdrop`; есть нативный путь Composition
и отдельный Acrylic. Это существующая основа, но не рабочая реализация жидкого окна.

Нынешний Popup — отдельный ShellWindow с собственной геометрией и смещением.
Одного изменения его привязки на верх экрана недостаточно для принятого UX.
Технический путь нужно выбирать под единое тело и постоянную навигацию.

## Что должна доказать будущая техническая проба

1. Непрерывный внешний силуэт: тонкий край, наведение, рабочие состояния разных размеров.
2. Локальное притяжение нижнего края к курсору и мягкий возврат без дрожания.
3. Читаемые и устойчивые текст/контролы во время деформации, согласованное раскрытие содержимого.
4. Быстрое перенаправление незаконченного перехода новым выбором.
5. Правильные прозрачность, сглаживание, тень и область приёма мыши вне силуэта.
6. Поведение на разных DPI/мониторах, фокус и допустимые состояния поверх fullscreen.
7. Ровные кадры, задержка от ввода, нагрузка при движении и отсутствие ненужной
   постоянной работы в покое; спокойный reduced-motion вариант.

Размеры, частота кадров, радиус влияния, амплитуда и параметры физики сейчас
не фиксируются произвольно. Их надо подобрать и проверить на реальном устройстве.
Чёрный материал из выбранного направления не требует заранее обещать сильную
оптическую рефракцию или сложное размытие ради самого эффекта жидкости.

## Порядок

Сейчас обсуждаем нужный motion и состояния. После подготовки концепции будущий
план должен предусмотреть отдельную проверку поверхности до миграции виджетов.
Если нативный путь не обеспечивает нужное качество, сначала пересматриваем
технический подход и явно обсуждаем компромисс; не выдаём обычный slide/fade
за согласованный жидкий эффект. Никакая проба этим документом не запущена.
