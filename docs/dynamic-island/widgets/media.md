# «Сейчас играет» — подготовка адаптации

2026-11-02. Обсуждение и read-only исследование, не спецификация реализации.

## Актуальное решение пользователя

Дальнейшую диагностику сейчас не проводить. При будущей переработке медиавиджета
нужно исправить получение/обновление обложки универсальным способом для разных
плееров и медиасессий. Точечная заплатка или отдельная интеграция только ради
Яндекс Музыки не соответствует запросу. Конкретный механизм ещё не выбран.

Пользователь уточнил симптом: теряется **только обложка**, название трека
и остальные данные не пропадают. Работу по исправлению выполнить позже,
в составе переработки виджета; сейчас достаточно зафиксированного требования.
Материалы ниже — уже полученные наблюдения, не повод продолжать проверку сейчас.

## Выбранная схема управления — вариант B

Пользователь выбрал интерактивное внешнее кольцо: обложка в центре служит
play/pause, кольцо управляет позицией трека, предыдущий/следующий расположены
по бокам. Постоянная лента и понятный источник сохраняются. Схема компактная,
показ — по необходимости.

Дополнение пользователя: значок play/pause не должен постоянно закрывать
обложку; он появляется только при наведении на неё. Вне наведения обложка
остаётся чистой, при этом вся её центральная область остаётся кнопкой.
Для доступности нужны семантическое имя действия и видимый клавиатурный фокус
без постоянного перекрытия изображения.

Перемотка и play/pause должны иметь отдельные зоны и жесты. Предложение автора:
жест, начатый на кольце, остаётся перемоткой до отпускания и не вызывает паузу
при пересечении центра. Точные размеры зон, preview времени, разрыв кольца
и способ применения перемотки ещё предстоит проверить; текущий выбор B
не является подтверждением этих технических деталей.

Выбор B зафиксирован по сообщению пользователя. В рабочей папке финальный файл
сравнительного листа пока не сохранён; в `sketches/media-v1/prompts.md` есть
подготовленный промпт. Это ограничение сохранённых материалов не отменяет
пользовательского выбора; точные параметры жестов и размеров ещё требуют проверки.

## Что сообщил пользователь

- Непонятно, откуда берутся обложки.
- При воспроизведении Яндекс Музыки пропадает только обложка; первоначальную
  формулировку «ничего не подтягивается» пользователь позднее уточнил.
- Медиавиджет должен стать заметно красивее и частью единого дизайна острова.
- Пользователь уточнил: отдельное приложение Яндекс Музыки, и включил
  воспроизведение для read-only проверки.

Первоначально это пользовательский отчёт о проблеме. Позднее выполнено чтение
живой медиасессии (см. ниже); отсутствие данных в UI оболочки пока не наблюдалось
автоматически. Приложение и воспроизведение не запускались/не менялись агентом,
продуктовый диагностический код не добавлялся.

## Что подтверждено текущим кодом

Прочитаны целиком `native/Shell/Media/MediaService.cs` и `native/Shell/Tail/MediaFlyout.cs`
соседнего репозитория `windows-shell`, просмотрены потребители в Dock.Tail и ShellHost.

- Источник — Windows GlobalSystemMediaTransportControlsSessionManager.
- Выбирается только `GetCurrentSession()`. Список всех сессий и пользовательский
  выбор проигрывателя в этой реализации не предусмотрены.
- Название, исполнитель и `Thumbnail` читаются из медиасессии. Прямого поиска
  обложек в интернете или интеграции с Яндекс Музыкой здесь нет.
- Обложка загружается из `Thumbnail`; поток больше 4 MiB не принимается,
  исключение загрузки возвращает пустой результат без отдельной диагностики.
- Если названия трека нет, модель текущего медиа становится пустой.
- `NowPlaying` содержит AppId, Title, Artist, Playing и доступность трёх команд.
  При равенстве этой модели текущему значению Refresh сразу возвращается.
- Перезагрузка обложки происходит только при изменении Title/Artist/AppId.
  Если поменялся только Thumbnail, обновление изображения может быть пропущено.
- В нынешнем UI есть обложка, название, исполнитель и предыдущий/пауза/следующий;
  доступность команд учитывается. При исчезновении текущего медиа popup закрывается.
- Тот же Cover используется в доке и медиапанели; это общий источник данных,
  а не два независимых механизма получения обложек.

## Что это позволяет заключить

Обложки не выбираются случайным поиском по сети: показывается изображение,
предоставленное выбранной сессией Windows. Это может не совпасть с ожидаемым
пользователем проигрывателем, если Windows выбрала другую сессию.

В коде есть конкретный сценарий пропуска поздней/обновлённой обложки при той же
модели трека. Однако связь именно этого сценария с Яндекс Музыкой пока не доказана.
На этапе чтения кода эти границы ещё не проверялись. Позднее сессия,
её выбор и поток Thumbnail проверены живым запросом (см. ниже). Порядок
событий и состояние внутри процесса оболочки остаются непроверенными.

## Что выяснить позже при переработке — не текущая задача

1. Способ использования выяснен: отдельное приложение, источник сессии
   `ru.yandex.desktop.music`.
2. Симптом уточнён пользователем: отсутствует только обложка, остальные данные есть.
3. Корректная сессия, выбранный источник и читаемая обложка на стороне Windows
   подтверждены для текущего воспроизведения. Нужно сопоставить это с внутренним
   состоянием MediaService и отображением в оболочке.
4. При будущей разрешённой проверке сопоставить первое получение метаданных
   и последующие события с загрузкой изображения. Отдельно проверить смену
   трека, паузу и несколько открытых проигрывателей.

Ни универсальный источник картинок, ни сервисная интеграция, ни конкретный fix
пока не выбраны. Исследование не переходит в изменение работающей оболочки.

## Направление визуальной переработки — предложения автора

- Читаемая обложка и ясная иерархия названия/исполнителя в общем теле острова.
- Понятное обозначение источника воспроизведения: должно быть ясно, чем управляем.
- Единый язык контролов и motion, без приклеенной старой карточки MediaFlyout.
- Продуманные состояния загрузки, отсутствия обложки и отсутствия медиасессии;
  оформление должно сохранять качество даже при неполных данных.

История первоначальных предложений ниже не заменяет актуальный выбор B выше.
Выбор проигрывателя, визуализаторы и автоматические появления при смене трека
по-прежнему отдельно не согласованы.

## Первоначальное предложение по функциям — история обсуждения

После остановки диагностики продолжаем проектирование виджета. Предложение автора:

1. Сохранить обложку, название, исполнителя и три команды воспроизведения;
   переработать их как содержимое общей поверхности острова с постоянной лентой.
2. Явно показывать источник воспроизведения. При нескольких доступных источниках
   дать выбрать, каким управлять; проверить поддержку и правила выбора позже.
3. Добавить прогресс трека, прошедшее/оставшееся время и перемотку, когда источник
   предоставляет достаточные данные и разрешает управление. Недоступное действие
   должно корректно отражаться в интерфейсе. Это расширение нынешнего виджета,
   а не уже реализованная возможность или принятое пользователем требование.
4. При отсутствии активного медиа показывать понятное пустое состояние внутри
   острова, сохраняя доступ к другим виджетам. Детали поведения пока не утверждены.

Эти предложения обсуждаются до отрисовки окончательных состояний. Автоматические
события смены трека, визуализаторы и отдельные интеграции сейчас не добавлены.
Диагностика приложения и воспроизведения остаётся остановленной.

## Последующая обратная связь пользователя — актуальная основа

- Медиавиджет появляется только когда нужен, как в текущем поведении.
  Это описывает контекстный показ и не отменяет общую настройку ленты.
  Сверка статического кода: в автоматическом режиме Dock.Tail вызывает
  `TempWidgetVisible("media", media != null)`. Поэтому пауза сама по себе
  не скрывает виджет, пока текущая медиамодель существует. Это описание
  нынешнего поведения, без нового опроса проигрывателя.
- Виджет должен быть достаточно компактным.
- Обложка одновременно является кнопкой play/pause. Предыдущий и следующий
  трек располагаются слева и справа от неё.
- Понятное обозначение источника принято. Это не отдельное подтверждение
  дополнительного выбора среди нескольких плееров; его правила ещё обсуждаются.
- Первоначально пользователь предложил рассмотреть прогресс и перемотку кольцом,
  отмечая возможный конфликт с play/pause. После сравнения описаний выбрал B —
  интерактивное внешнее кольцо; play/pause появляется только при наведении.

Нужно сравнить варианты и явно разделить действие центра и перемотку. Кандидаты
для обсуждения: кольцо только показывает прогресс, а перемотка доступна отдельно;
интерактивное внешнее кольцо с разделением зон/жестов; компактная линейная шкала
как контрольный вариант. Позднее выбран B, подробности в актуальном решении выше.

Предложения автора для оценки вариантов: пропавшая обложка не должна лишать
центральной кнопки play/pause; перемотка не должна случайно переключать паузу.
При неизвестной длительности или недоступной перемотке интерфейс не изображает
несуществующую возможность. Для интерактивного кольца отдельно проверяются
ширина зоны попадания, начало/конец шкалы, preview времени и доступность с клавиатуры.
Это критерии будущей проверки, не выполненные тесты или выбранная реализация.

Эти контракты не подтверждают, что конкретная версия Яндекс Музыки сейчас
передаёт нужные данные во всех условиях. Для конкретного воспроизведения
ниже выполнена отдельная проверка.

## Живая read-only проверка 2026-11-02

Пользователь самостоятельно включил отдельное приложение. Через существующие
WinRT API в отдельном короткоживущем PowerShell-процессе прочитаны список сессий,
текущая сессия, метаданные и поток Thumbnail. Команды воспроизведения, выбора
трека и настройки не отправлялись. Продуктовый код/сборка не менялись.

- Сессия ровно одна, текущая — `ru.yandex.desktop.music`, статус `Playing`.
- Название — «Двери вагона», исполнитель — Fluxyluv, AlbumTitle пустой.
- Thumbnail существует; поток успешно прочитан: 35 204 байта, `image/png`.
- Изображение успешно декодируется в 150×150. Это ниже ограничения 4 MiB
  в нынешнем MediaService, поэтому превышение размера для этого случая исключено.
- Снимок конфигурации: медиавиджет включён (`media.enabled=true`).
- DLL из действующего publish имеет ProductVersion
  `1.0.0+b40eee44c97b42b66ca3a5a52c64cea5072e8b8e`.

Данные: [yandex-media-2026-11-02.json](../diagnostics/yandex-media-2026-11-02.json).
Полученная из Windows обложка:
[yandex-current-cover-2026-11-02.png](../diagnostics/yandex-current-cover-2026-11-02.png).
Это диагностический материал текущего трека, не собственная иллюстрация проекта.

Таким образом, для проверенного воспроизведения нельзя объяснять проблему
полным отсутствием сессии/метаданных/обложки у Яндекс Музыки, выбором другой
сессии, выключенным медиавиджетом или слишком большой обложкой.
Причина конкретного пропадания в UI ещё не подтверждена. Подозрение на пропуск
позднего обновления изображения в Refresh сохраняется как гипотеза; не доказано,
что это единственная причина. Не исследовано внутреннее состояние MediaService
в процессе оболочки и загрузка BitmapImage в её UI-потоке.

Попытка осмотра UI через Computer Use не дала целевого окна оболочки: в списках
окон/приложений WindowsShellNative не был доступен. Пользователь затем сам
уточнил: отсутствует только обложка. Дальнейшую диагностику сейчас остановил.
